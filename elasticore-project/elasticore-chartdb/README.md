# elasticore-chartdb

[한국어](README.ko.md)

Converts between a [ChartDB](https://github.com/chartdb/chartdb) diagram (the JSON that
"Export > JSON" writes and "Import > JSON" reads) and an ElastiCORE blueprint, in both directions.

```
ChartDB diagram JSON  --to-yaml-->  <blueprint>/<domain>/env.yml
                                    <blueprint>/<domain>/model/*.yml
                                    <blueprint>/chartdb.yml          (sidecar)
ChartDB diagram JSON  <--to-json--  the same blueprint, with or without the sidecar
```

## Use

```bash
# diagram -> blueprint
./gradlew :elasticore-project:elasticore-chartdb:chartdbToYaml \
    -Pjson=shop.chartdb.json -Pblueprint=src/main/resources/blueprint \
    -Pdomain=shop -Ppackage=com.acme.shop [-Pexpose=20] [-Pforce=true]

# blueprint -> diagram
./gradlew :elasticore-project:elasticore-chartdb:chartdbToJson \
    -Pblueprint=src/main/resources/blueprint -Pjson=shop.chartdb.json [-Pdatabase=postgresql] [-Pname=Shop]

# there and back; reports anything that did not survive
./gradlew :elasticore-project:elasticore-chartdb:chartdbVerify -Pjson=shop.chartdb.json [-Pwork=build/chartdb-verify]
```

Relative paths are resolved against the repository root. The same commands are available as
`io.elasticore.chartdb.ChartDbConverter to-yaml|to-json|verify --key=value ...`.

## What goes where

The model goes to the DSL; the picture, and what a database knows that the DSL has no word for,
goes to the sidecar `chartdb.yml`. The sidecar holds only the difference between the diagram and
what the blueprint already says, so the model is never described twice.

| ChartDB | Blueprint DSL |
|---|---|
| table, schema | `entity @table(name) @schema(name)`; one `model/<schema>.yml` per schema |
| view, materialized view | `entity @immutable` (materialized: flag in the sidecar) |
| column type, size, precision/scale | DSL type, `string(40)`, `decimal(12.2)` |
| a type the DSL lacks (`jsonb`, `inet`, arrays, ...) | nearest DSL type + `@columnDef('...')` |
| NOT NULL / primary key / auto increment / UNIQUE | `!` / `@id` / `@sequence` / `@unique` |
| default | `@default(...)` |
| column and table comments | `-- comment` |
| foreign key (many-to-one, one-to-one) | entity reference, `@OneToOne` |
| foreign key that is part of a composite key | `@id @fk(Entity.field)` |
| many-to-many | `List<Entity> @ManyToMany` |
| index | `@Index(name=..., columnList=..., unique=...)` |
| check constraint | `@check("...")`, and `@min`/`@max` where it is a range |
| enum custom type | `enum @db(code) @json(code)` in `model/enum.yml` |
| composite custom type | `entity @embeddable`, used with `@Embedded` |

In the sidecar: table position, size, colour, order and area; areas; notes; view dependencies;
index type (btree, gin, ...) and comment; collation; relationship names; and any single value the
DSL form cannot carry exactly (for example the original text of a comment that had to be rewritten).

A blueprint without a sidecar converts too: tables are laid out in columns and each domain
(bounded context) or schema becomes an area.

## Verified

- `samples/shop/shop.chartdb.json` (online shop: member, catalog, inventory, sales, shipping,
  report; 28 tables, 34 relationships, 12 custom types, 6 areas, 2 notes, 4 view dependencies) goes to
  a blueprint and comes back byte for byte. It is generated by `samples/shop/build_shop_erd.py`.
- ChartDB's 50 bundled template diagrams round-trip with no difference
  (`./gradlew :elasticore-project:elasticore-chartdb:test -Dchartdb.extra=<dir of json>`).
- The blueprints of `elasticore-sample-petstore` and `elasticore-template-ddd` convert to diagrams
  that ChartDB's own import schema accepts.
- The blueprint written from the shop diagram is accepted by `elcore3`, and the generated code
  compiles (hexagonal and ddd on Spring Boot 4; layered on Spring Boot 3).

## Limits

- ids are not kept: ChartDB assigns new ones on every import, so diagrams are compared by name.
- A view's SQL is not part of ChartDB's diagram format, so there is none to convert.
- A view without a primary key gets one column marked `@id` in the DSL (JPA needs one); the diagram
  keeps the column as it was.
